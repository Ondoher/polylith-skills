# Assessment: moving skill operations behind MCP

The repository is well positioned for an MCP service because most mechanical work already lives in reusable JavaScript modules. The useful change is to give agents short, stable operations for reading, delivering, validating, assembling, and saving work. The service can reuse existing domain code while removing generated shell commands, one-off wrappers, and copied handoff payloads.

The owner expects practical, proportionate execution with extensive reuse of existing work. The earlier engineering-day ranges were not grounded in our agent-assisted development pace and are withdrawn. The reference to a couple of hours corrected those expectations; it did not impose a time budget. Reuse the existing transport probe, domain modules, schemas, writers and tests, and demonstrate a working integration with explicit completion evidence for each migrated operation.

This is an assessment, not authorization to migrate, install a persistent service, alter agent authority, or resume the paused Alexa refinement.

Most of these are library calls already. Six modules expose no exports: the installer, review context fingerprint, format preflight, folder standards, standards attestation, and single-pass CLI. The single-pass CLI can be bypassed through `DesignRecords`, `DesignRun`, and `DesignAssembly`. Some APIs intentionally take filenames, including model/artifact commit and exact review binding. A server-owned staging file can satisfy those contracts without the parent reading and reproducing the JSON. Eliminating all disk I/O would require a broader redesign and is not necessary for the first migration.

The initial inventory found two `workspace-write` authoring roles and 14 `read-only` roles. The owner subsequently authorized permission preparation before restarting VS Code: all 16 now use `workspace-write` and explicitly permit scoped file/MCP result delivery. A service runs with its own filesystem authority, so an agent's local sandbox must not be treated as enforcement of service permissions.

The default server connection must not trust an arbitrary `role: "parent"` argument. Establish scoped assignments/capabilities for read, proposal submission, review result submission, and authorized commit. Verify how the installed Codex host carries these assignments in a small live test. Do not add a new per-request approval ceremony for operations already authorized by the current task.

## New service responsibilities

1. **Process and installation lifecycle.** One shared localhost service, discovery/health, owned configuration, version binding, reconnect/restart and shutdown. Updating linked skill code must not leave a running server using stale imported modules. The latency probe is not this managed runtime.
2. **Product/run handles and bounded responses.** Resolve paths once, retain exact source/model identities, batch useful record selections, return one representation of data, and use handles for downstream mechanical consumers. Respect existing output limits and explicit continuation; a 58 KB transport benchmark does not authorize returning 58 KB to an agent in one response.
3. **Useful operations.** A modest initial surface might cover open/resume run, prepare stage, read records, submit units or saved proposals, assemble candidate, prepare/record review, authorized stage commit, render, status and metrics. These are proposed responsibilities, not a finalized tool catalog. Hundreds of exported functions should not become hundreds of model-visible tools.
4. **Concurrency and long jobs.** Serialize conflicting writes per product, retain expected-version checks and existing locks, make retries idempotent, and isolate long renders/builds/installers in workers so they do not block small reads. Some current helpers use synchronous filesystem and child-process operations.
5. **Persistence and freshness.** Use RAM as a cache over current durable artifacts initially. Revalidate relevant source/current-pointer identities before commits and review-dependent operations. Preserve completed units, resume receipts and rollback baselines after interruption. Treat malformed independent units as repair issues while continuing valid work.
6. **Verification and instrumentation.** Record queue, load/cache, validation, assembly/render, serialization and send timings independently, plus bytes and version identities. Server timings alone cannot measure model processing or the full agent wall clock.

RAM-only working state with disk writes exclusively on an explicit save command is a separate storage-policy choice. It changes checkpoint, exact-review and recovery behavior. Preserve the existing durable store for this migration unless the owner selects that additional change.

## Execution expectations

The [self-driven migration plan](mcp-migration-plan.md) now owns the execution sequence and six reportable goals. It supersedes this assessment's provisional schedule. The owner's direction is to emphasize positive cases initially and reserve broad reviews for larger integrated results; a more complete testing pass follows later.

Completion requires working calls and verified outputs across the entire agreed migration scope, with no required work remaining. The refinement path is the first milestone, not a sufficient stopping point. The coverage ledger distinguishes implementation, instruction connection and verification. Working milestones determine progress. Record time for performance diagnosis and reporting; elapsed time alone is not a stopping condition.

Assumptions: preserve current canonical schemas and validators, reuse the working filesystem store, retain independent review, support only current data contracts in permanent code, avoid a new database or agent-hosting framework, and use one ordinary attended run for outcome validation. One-off development-data mutations or conversions are allowed to reuse prior work; any helpers remain disposable development tooling and must not become runtime compatibility code or permanent migration APIs. Removing full-model proposal requirements or changing review invalidation semantics is a separate design change outside this transport integration. Byte-identical module consolidation is optional cleanup, not a prerequisite.

## Performance judgment and recommended first scope

The [HTTP experiment](mcp-http-latency-experiment.md) measured approximately 3–5 ms median direct round trips and 4.85–6.99 ms for actual Codex tool intervals, but 30.592 seconds for five sequential agent calls. The [STDIO experiment](mcp-stdio-sharing-experiment.md) found separate server instances per tested agent. Together they support an explicit shared HTTP service, with fewer model-mediated operations as the performance objective.

Simply wrapping today's CLI commands one-for-one would preserve most calls and large payloads. In particular, `buildPlannerInput` still returns `productModel: chain.model`, and the refinement skill still requires one complete semantic model proposal for a changed description. MCP does not automatically remove those costs, instruction loading, UX/UI reasoning, or review passes.

Start with **the parent preparation and UX/UI handoff path**: scoped verified inputs, reusable stage preparation, direct unit delivery, assembly, exact review subjects and parent-authorized commits. Retain the current stored format. This directly targets the one-off persistence wrapper, handoff helper, long assignment construction and repeated retrieval observed in the attended run. Keep semantic choices and document organization with their existing agents.

Compare the same saved workload against the existing path with equivalent required information and identical output limits. Measure useful-output latency, number of model-mediated calls, agent-generated argument bytes, returned bytes, validation/repair results and source/review equivalence. Initially demonstrate positive fixture equivalence, successful delivery/reuse, shared run access and a small live integration. Record interrupted/retried deliveries, stale updates, restart recovery and comprehensive rollback tests in the later complete test pass unless a concrete failure requires attention sooner. Use scripts for most validation; no paid full-product baseline is needed to establish the first benefit.

Success is less generated plumbing, fewer handoff turns, and reusable exact results with equivalent behavior. The experiments establish that localhost HTTP is fast enough to investigate this route; they do not establish a sub-minute refinement outcome.

Codex supports localhost HTTP MCP configuration and server instructions, which provide an official integration route ([documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)). The service, scoped operation contracts, and workflow changes assessed here remain repository work to implement.
