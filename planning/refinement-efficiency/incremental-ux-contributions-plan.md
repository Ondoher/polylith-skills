# Incremental UX contributions: implementation plan

Status: completed, 2026-09-29. Implementation, deterministic reconstruction and
one isolated first UX authoring round are complete; see the
[execution report](incremental-ux-contributions-execution.md) for measurements,
decisions, verification and retained defects. Contributions are now the preferred
MCP transport for UX updates against a saved baseline. The canonical UX schema
and its review gates remain unchanged. The multi-read skill and forced-batching
investigation remain deferred. Retain the larger read window and use parallel reads
when available, without making successful batching an authoring prerequisite.

## Objective and evidence

The owner's goal is elapsed time close to useful UX reasoning, with independent
reasoning parallelized where it helps. Optimize the model work required to
represent and deliver its decisions: reconstructing old records, selecting and
checking schema fields, tracking references, generating repetitive output and
repeatedly preparing tool calls. Tool execution and return are already fast in
the measured examples. Faster disk writes, transport or assembly are not the
target of this change; saving is a way to retain decisions without another model
pass over their representation.

Data size is a secondary observation. Reject a smaller representation if it
increases reasoning about encoding, lookup, bookkeeping or reconciliation.
Prefer straightforward names and familiar UX concepts, even when they use more
text. Avoid positional encodings, abbreviation dictionaries, or an elaborate
operation language introduced only to compress payloads. Mechanical identities,
revisions, indexes and receipts are generated by code, not reasoned out by the
author. Smaller output is valuable here only when it removes model work.

Save useful UX contributions as they are decided, then construct the first UX
proposal mechanically. The agent should generate new meaning and changes once;
it should not reproduce unchanged records, author packing metadata, or generate
a final combined JSON response.

The [last full replay](ux-full-native-replay-20260929.md) spent 25m02s emitting five
large replacement commands during its first authoring round. About 77.2% of the
final four changed units was unchanged value content. One 3m36s rewrite corrected
only `outcomecome` to `outcome`. These measurements identify the target, not a
promised time saving: useful new content and decision work still require generation.

The earlier [packet experiment](packet-assembly-experiment.md) increased payload
size by 11.16%. Measure envelopes and references honestly, but do not make byte
reduction a prerequisite or success criterion. The first local check must show
that code takes over reconstruction and bookkeeping without demanding a more
complicated representation from the agent. Merely splitting complete JSON into
packets is insufficient.

## Reuse the current implementation

The current MCP operations already open bound stores, import existing UX, read
assigned units, accept deliveries and assemble candidates. Their granularity is
the problem: `units.deliver` takes complete context, element or flow records, and
`DesignRun.deliver` requests another complete unit when a repair fails.

Extend these boundaries:

| Existing code                                     | Planned responsibility                                                                                            |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `scripts/mcp/DomainOperations.mjs`                | Register scoped contribution and completion operations; enforce ownership of every affected unit.                 |
| `skills/refine-design/scripts/design-records.mjs` | Reuse exact bindings, identities, atomic persistence and prior-version checks.                                    |
| New focused helper beside the design scripts      | Validate small contribution types, retain batches, resolve stable record IDs and materialize affected units.      |
| `design-assembly.mjs` / `design-run.mjs`          | Reuse packing, native unit construction, structural validation and repair notices.                                |
| UX role and `single-pass-design.md`               | Author and submit bounded contributions as work proceeds; finish with a receipt instead of full replacement JSON. |

Keep canonical UX schema 0.4 and its publication, UI and later technical consumers.
The contribution format is scratch authoring transport, not a second product
model or a backward-compatibility adapter. Start with UX; UI transport changes
can follow measured results without expanding the first experiment.

## Concrete authoring contract

Implemented operations are `units.status`, `units.contribute` and `units.finish`.
Their maintained contract is [incremental UX authoring](../../skills/refine-design/references/ux-contributions.md).
The original milestones and decision rule below describe the completed work;
the execution report records deviations and evidence limits.

The parent imports the current baseline once, or opens an empty bound store for
initial processing. It supplies the agent with assigned unit IDs and compact
record identities. The agent contributes semantic pieces within those units:

- Context: one source binding, feature, question or realization entry.
- Element: one surface, component, action, feedback record, or identifiable
  interaction-frame region/affordance.
- Flow: flow metadata, a step, an alternate, a decision, or a field change.

Use a small closed set of operations for defining records, setting supported
fields, explicit insertion/order changes, and removal. Define field names and
legal targets from the current schema. Common typed variants map values directly
to canonical fields. Do not introduce an endpoint per field or permit executable
transformations and arbitrary JSON paths from the author.

For example, a batch can express this correction without reproducing
the flow. The IDs below illustrate the shape:

```json
{
  "stage": "ux",
  "batchId": "edit-03",
  "base": { "flow:edit-video": "revision-2" },
  "changes": [
    {
      "unit": "flow:edit-video",
      "op": "set",
      "target": [{ "collection": "alternates", "id": "resume-follow" }],
      "fields": { "outcome": "Bring the resolved playhead into view and resume following." }
    }
  ]
}
```

Here the agent names the schema field, value and stable target; code validates
the field and edits the existing record without reconstructing its siblings. Unknown
operation types or fields are rejected before they enter the working record.
Other supported changes share the same batch rather than requiring separate
calls. Existing field values remain untouched unless explicitly changed.

Save useful pieces at natural decision boundaries, grouping nearby ready
contributions into one call. Do not interrupt continuous UX reasoning just to
flush a tiny field or reach an arbitrary byte threshold. Start by measuring
batches around 5–20 ready contributions; keep them small enough to avoid a final
reconstruction pass, but large enough to avoid repeated call-planning and model
resumption overhead. Batch sizes are tuning parameters, not correctness limits.
Do not truncate meaningful text or wait for an entire large workspace.

Partial records and forward references are allowed. A flow may refer to a dialog
before its definition arrives. Stable IDs identify meaning independently of
publication hierarchy; explicit ordered references or insertion anchors preserve
flow order. The assembler must not infer missing behavior, priority, research
evidence or acceptance status from a template.

## Storage, completion and recovery

Each batch submission durably saves its contribution data and returns a compact
receipt: accepted batch/record IDs, new revisions, pending requirements and repair
notices. It does not echo accumulated data. Batch IDs make exact retries reusable;
reuse of an ID with different content reports a conflict. Prior revisions prevent
silently overwriting another contribution. Keep the current one-owner-per-unit
rule; independent owners can contribute to separate units.

Use saved baseline handles and immutable batch data in the existing scratch run,
plus a compact manifest. Index records and pending references mechanically. Do
not regenerate, rewrite or revalidate the entire growing product after each
small contribution. On restart, replay the saved baseline and accepted batches
once, then continue from the last acknowledged receipt. Temporary files may
carry unusually large batches through the same validation and capability checks.

Validate the submitted fields immediately. Separate missing-but-expected fields
or references from malformed contributions. Keep valid independent contributions
when one fails; dependent changes must be accepted together or remain pending.
Return an exact target and remedy. Never silently correct ambiguous field names.

At `units.finish`, the author declares its assigned work delivered. Code resolves
available references, supplies mechanical metadata, computes packing/defaults,
and materializes the current complete authoring units once. Its work should scale
with baseline records, contributions, references and generated bytes, using
indexes rather than repeated whole-product searches.

Missing meaning becomes a visible repair notice with a targeted remedy; good
siblings remain available. Delivery completion is distinct from structural
readiness, semantic acceptance and review approval. The agent's final response
contains only the saved proposal handle and status. There is no final authoring
pass to restate accumulated content.

## Implementation milestones and checks

1. **Define the smallest sufficient contract.** Inventory fields changed in the
   four captured units and define the necessary contribution types, identity,
   ordering and ownership rules. Cover the large document context and video
   workspace as well as flow steps. Deliverable: a small closed schema and an
   example batch for each affected record family.
2. **Build the deterministic path locally.** Implement contribution persistence,
   immediate validation, receipts, restart and final materialization. Verify
   successful creation, field changes, insertion, baseline reuse and resumed
   batches. Include targeted checks for unknown fields, stale revisions and exact
   retries because those are central to this operation. No paid agent or broad
   application review is needed for these local cases.
3. **Replay retained output without a model.** Mechanically express the four
   captured initial units as contributions against their original baseline.
   Reconstruct those target values exactly, preserving known first-output defects
   as explicit fixture expectations rather than claiming they are valid UX.
   Separately demonstrate schema-valid new-record construction from an empty
   store. Exercise the one-field correction without resending its flow. Measure
   contribution bytes including envelopes, calls at proposed batch sizes,
   validation/materialization time and retained-data reuse. Inspect the author's
   required choices and lookups as well: fewer bytes must not conceal a more
   difficult encoding task. This is a construction feasibility check, not proof
   that a model will author good deltas or reason less.
4. **Integrate one UX author and instrument the first-pass boundary.** Update its
   existing role/workflow guidance; do not add another skill or assembly agent.
   Count built-in discovery calls such as `tool_search`, which the current
   collection analyzer omitted. Capture direct/deferred tool exposure, actual
   grouping, model/effort, input identities and the exact submitted contracts.
5. **Run one isolated first UX round after authorization to execute.** Reuse the
   saved Alexa input baseline, preserving live files. Do not give the agent the
   old completed answer. End when code has saved the agent's first proposal as
   existing authoring units. The materialization necessary to deliver those units
   belongs inside the measured authoring boundary; subsequent parent document
   assembly, canonical promotion, independent review and rework remain excluded.
   Record defects without launching another design round. Retain every batch and
   receipt for focused continuation.

Use the checkpoint adviser at completed milestones with the owner's standing
preapproval of suggested messages. Concentrate any wider review on the integrated
contribution/storage change, rather than reviewing every individual operation.

## Measurements and decision rule

The primary question is whether the agent spends less effort converting its
decisions into deliverable records. A smaller payload is useful evidence, but
not sufficient if it requires more bookkeeping, schema reasoning or model turns.
Record the observed work around each contribution: new UX decisions, retrieval,
representation, correction and delivery. These are activity labels with explicit
limits, not measurements of the model's private thought process.

Report preparation, collection, initial decisions, contribution generation,
submission/validation, final materialization and total time through first
delivery. Continue to distinguish observed output streams, reasoning-item streams,
tool intervals and unattributed gaps; do not equate these with pure design thought.

Also record total generated argument bytes, contribution count, call count,
batch sizes, unchanged data retransmitted, time to first durable contribution,
recovery cost and final completeness. Keep actual usage counters separate from
credit estimates. Include all preparation in the end-to-end total, even when
also reported separately.

Server validation, persistence and materialization timings are diagnostic checks
that mechanical work remains inexpensive. Do not spend the optimization effort
shaving fractions of a second from them while model representation work takes
minutes. Compare call-generation and between-call intervals as well as emitted
bytes so increased interaction overhead cannot masquerade as improvement.

Advance to the paid test when the local replay preserves exact content, avoids
whole-unit reconstruction for small edits, retains all required UX meaning and
provides a straightforward authoring contract. There is no byte-reduction quota.
If the author must learn a compact encoding, calculate references, repeatedly
look up field positions or plan more calls, simplify the contract before testing
it with a model. Local checks cannot prove a reasoning improvement; the live
trial must assess that, with observed activity and timing limits stated.

Adopt the method only if the live first-pass evidence shows reduced model
representation/delivery work and useful total-time improvement without moving
required design work into a later generation stage. Reject a smaller payload
that increases reasoning or bookkeeping burden. Prefer targeted fixes and
replay of affected batches over restarting a
full refinement. Do not claim initial-product savings from an update-only test;
the empty-store construction check covers correctness, while live cold-start
performance remains separately unmeasured.
