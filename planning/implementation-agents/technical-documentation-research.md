# Technical-documentation research

These findings inform the [technical-documentation contract](technical-documentation-contract.md). They are general guidance for an implementation-facing architecture guide, not product decisions or requirements to copy a third-party template in full. Sources were checked on 2026-09-23.

## Findings and resulting choices

1. **Document the architecture at a few useful levels.** [arc42's overview](https://arc42.org/overview/) organizes architecture around context, building blocks, runtime, deployment, decisions, quality, and risks. Its [lean guidance](https://docs.arc42.org/tips/5-3/) calls for a top-level building-block view even in a small document. The technical guide adopts those concerns as content groups, while publishing only pages with useful content rather than reproducing all twelve arc42 sections.

2. **Choose diagrams for the question they answer.** The [C4 model](https://c4model.com/diagrams) says context and container diagrams are sufficient for many teams and deeper component or code diagrams should add value. Its [diagram checklist](https://c4model.com/diagrams/checklist) emphasizes a clear title, scope, named elements, and meaningful relationship labels. Use a context/runtime diagram to explain major boundaries; add a component or sequence diagram for a difficult flow. Keep code-level structure in source or generated code navigation during active development.

3. **Spend detail on a few critical scenarios.** [arc42's runtime-scenario advice](https://docs.arc42.org/tips/6-2/) prioritizes scenarios that reveal important processing, quality goals, risky behavior, or unstable external interfaces. Select flows by architectural consequence rather than documenting every product action. For each selected flow, describe who owns the state, what must succeed together, failure and cancellation effects, and what evidence would verify the proposed guarantee.

4. **Make quality goals and consequential decisions explicit.** [arc42's quality-goal advice](https://docs.arc42.org/tips/1-16/) favors a short set of prioritized goals explained through scenarios. Its [decision guidance](https://docs.arc42.org/tips/9-1/) focuses on choices affecting structure, quality, dependencies, or interfaces. For each significant accepted decision, record a stable identity, the context, choice, alternatives that mattered, consequences, and status. [AWS's ADR guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html) supports preserving a superseded decision's history rather than silently rewriting why it was made. This project can use compact decision sections initially and split them into linked records when their number or complexity warrants it.

5. **Separate explanation from contract reference.** [Diátaxis](https://diataxis.fr/start-here/) distinguishes explanation, which develops understanding, from reference, which supports accurate work. The architecture pages explain why boundaries and choices exist; critical-flow and interface pages state exact agreed behavior. Procedural build and test instructions remain in repository guides and are linked from the handoff page.

6. **Keep code evidence close to its source.** [arc42's source-code advice](https://docs.arc42.org/tips/8-8/) recommends linking to maintained code or tests rather than copying large snippets, which become stale. Record the inspected repository revision and relevant uncommitted paths, link to representative code and tests, and distinguish observed behavior from target decisions. Check local links and Mermaid syntax as part of publication. These checks support accuracy but cannot independently prove that the proposed architecture has been implemented.

7. **Let a complex issue have its own linked document.** [arc42's architecture-decision guidance](https://docs.arc42.org/section-9/) allows consequential decisions to live in central or local sections, and [C4's diagram levels](https://c4model.com/diagrams) allow a selective zoom into one part of a system. This supports a short general architecture guide linked to a few deeper issue documents. The issue document should own its detailed reasoning and contracts, while the overview retains only a summary and link; neither source requires every subsystem to have a separate document.

The remaining project-specific choices belong to the product owner and technical assessment roles. General documentation guidance cannot decide a product's persistence, media, or export guarantees.
