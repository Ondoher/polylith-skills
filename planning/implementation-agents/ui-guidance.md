# UI Guidance

Status: initial primary-source synthesis, 2026-09-16. Supports the installed assessment-only [UI designer](ui-designer.md); guidance does not itself change product decisions. [Source notes](ui-research.md) hold provenance, limits and conditional numeric checks.

## Authority And Inputs

Start from the owner's domain knowledge, accepted visual identity and UX [interface inventory](ux-planner.md#ux-to-ui-handoff). Preserve tasks, terminology and interaction intent. Label visual proposals and return behavior-changing placement/grouping decisions to UX and the owner. These are planning practices, not a second engineering standard or evidence of product usability.

Resolve applicable canonical obligations and overlays. Our [CSS/layout rules](../../documentation/standards/code-conventions.md#markup-css-and-layout), [React ownership](../../documentation/standards/react.md#css-and-layout-ownership) and [MUI theme/branding rules](../../documentation/standards/mui.md#styling-responsibility) remain authoritative. Reuse their Grid, CSS-owned styling, shared-variable and semantic-theme conventions; do not copy a source design system's component implementation or palette into the product.

## Compact Practices

1. **Spacing communicates relationships.** Use a small reusable spacing scale; distinguish internal padding, gaps within control groups, and separation between groups/regions. Keep related controls perceptibly closer than unrelated groups and repeat alignment/gap patterns. Density is contextual: preserve useful expert information rather than expanding every margin. Example: boundary controls form one group, separate from project commands. Assign scale ranges to compact internals, component/group spacing and region separation; allow small optical adjustments for visual balance. These categories do not impose an 8-pixel rule. [Carbon spacing](https://carbondesignsystem.com/elements/spacing/overview/).

2. **Typography uses roles, not arbitrary sizes.** Define coordinated heading, body, label, supporting-text and numeric-display styles through size, weight and line height. Match emphasis to information hierarchy; a task-heavy editor need not use marketing-scale headings. Evaluate actual fonts and representative content before choosing values. Owner preference: when proposing new typography, prefer families from Google Fonts unless accepted app typography or task-specific needs call for another choice; explain exceptions. Include suitable fallbacks and verify required weights, glyph coverage, numeric features where relevant, and licensing before claiming readiness. This is a font-source preference, not a requirement to load fonts from a remote service. Do not claim a universal minimum font size or copy Carbon's font/scale as a requirement. [Carbon typography](https://carbondesignsystem.com/elements/typography/overview/).

3. **Color expresses meaning consistently.** Specify surface, text, border, action, selection, focus and status roles across supported themes. Preserve a role's meaning when its value changes. For MUI apps, start from the target version/mode's palette defaults and preserve app overrides; framework defaults are not missing requirements or branding decisions. Keep identity optional and small: one to three purposeful colors, excluding derived shades; map them into suitable theme roles explicitly. Separate product branding from ordinary interaction/status roles; propose concrete identity directions when requested, clearly unaccepted until owner agreement. Do not implement unapproved branding. Check actual foreground/background pairs, including relevant states. Color cannot be the only cue for meaning. [Carbon color](https://carbondesignsystem.com/elements/color/overview/), [WCAG 1.4.1](https://www.w3.org/TR/WCAG22/#use-of-color).

4. **Contrast applies to content and meaningful controls.** Check readable text and necessary graphical state/identification cues, not just the default screen. De-emphasis must not make essential information unreadable. WCAG distinguishes text, large text, non-text cues and exceptions; apply the actual scoped criteria rather than one ratio to every border or disabled element. [Text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html).

5. **Control emphasis follows the task.** Make the principal action distinguishable from secondary and destructive actions; retain meaningful action labels and consistent placement. GOV.UK's single-primary-action advice suits its transactional pages; adapting it to an editor means clear hierarchy within meaningful task regions, not one primary button for an entire application. This regional adaptation is our inference, requiring domain evaluation. Do not change command availability or workflow to simplify appearance. [GOV.UK buttons](https://design-system.service.gov.uk/components/button/).

6. **Specify states, not only a polished default.** Describe relevant focus, hover, selected, disabled, loading, empty, error and completion treatment against the UX inventory. Distinguish focus from selection. Important status must remain perceivable without unnecessarily moving focus or announcing every update. Extra hover/focus content needs appropriate dismissal and persistence behavior. [Carbon states](https://carbondesignsystem.com/elements/color/overview/#interaction-states), [APG keyboard](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/), [status](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [hover/focus](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html).

7. **Plan adaptation explicitly.** Distinguish fluid editing regions from bounded forms/content; define shared alignment and what stretches, wraps, scrolls or changes arrangement as the window narrows or text grows. Preserve meaningful reading/focus order and access to controls. Test long labels, larger text and user spacing overrides, not just ideal sample content. A justified two-dimensional editing surface does not exempt surrounding forms and controls from applicable reflow requirements. Text-spacing thresholds are tolerance checks, not mandatory authored defaults. [Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [text spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html).

8. **Design the activation area.** Specify usable hit areas and separation, not merely icon dimensions. A small glyph can have a larger target. Target-size minima and their exceptions are conformance conditions, not ideal sizing for every user/input device. Keep precision and density choices explicit. [Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

9. **Prefer native behavior and established widget patterns.** Specify accessible names, semantic intent, keyboard behavior and focus movement with the visual design. ARIA alone supplies neither keyboard handling nor appearance. Follow established accessibility patterns by default. For an input dialog, normally place initial focus on the first enabled, relevant content input, not automatically on the footer action or close icon. For long or structured content, focus the title or introductory static content when needed to preserve reading order and visibility. For an informational dialog with no other controls, normally focus Close. For a dialog containing only action buttons, normally focus its designated default action. Retain the content-first exception for long or structured information. For a difficult-to-reverse confirmation, prefer the least destructive appropriate action rather than blindly focusing a destructive default. Specify contained Tab/Shift+Tab movement, Escape dismissal and focus restoration to the invoker or a logical next task target. Choose the target for the task, not solely its visual position. This applies WAI-ARIA APG guidance (checked 2026-09-17), not a claim that every dialog must focus its first input. [APG first principles](https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/), [modal pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

10. **Shape and surfaces form a coordinated system.** Define a small radius family by use; coordinate border width/color for separation and states, and focus treatment with component shape. Specify surface and elevation roles together, using surface differences as well as shadows where needed across themes. Do not make every container elevated. [Radius](https://atlassian.design/foundations/radius), [border](https://atlassian.design/foundations/border), [elevation](https://atlassian.design/foundations/elevation).

11. **Icons share a visual vocabulary.** Use recognizable meanings and a consistent family/style, size and optical alignment with text. Distinguish glyph size from activation area. Preserve the MUI-first source preference; explain exceptions and verify meaning in context. [Iconography](https://atlassian.design/foundations/iconography).

12. **Arrange forms around shared alignment and local spacing.** Align major content groups to consistent edges or columns; keep gutters and outer padding clear. Use shared spacing tokens inside each group rather than forcing every field, button or icon onto the page grid. Add an internal grid when it makes relationships clearer. Bound form widths to keep related content together; adapt columns as available space changes while preserving meaningful reading and focus order. As our form-specific application, group related fields and keep helper/error text with its logical input. Dialogs establish their own internal alignment rather than inheriting the underlying page grid. These principles also apply to forms within a workspace; they do not prescribe a grid for the whole editor. Column counts, breakpoint values and maximum widths remain app decisions. [Atlassian grid](https://atlassian.design/foundations/grid), publisher guidance checked 2026-09-17; form-specific adaptation is our synthesis.

## Scope And Handoff

Ordinary controls retain semantic/native behavior, keyboard access and visible focus even without a separate accessibility requirement. Favor readily accessible technology when otherwise comparable. Full equivalents for specialized app surfaces are not automatically commissioned; this never waives applicable standards or an agreed conformance target. See the established [accessibility scope](ux-guidance.md).

For app-wide planning, synthesize only foundations supported by supplied UX: shared scales, roles and recurring patterns, illustrated on representative surfaces. Explain variants and owner choices; preserve the [proposal/acceptance boundary](design.md#app-wide-ui-foundations-proposal). Reuse the accepted application reference in later specifications.

Deliver concrete layout constraints, tokens/values, states, adaptation and accessibility details through the [UI-to-view handoff](design.md#ui-design-agent). Preserve unresolved decisions. Validate representative tasks and content at relevant sizes/themes with keyboard and appropriate accessibility checks. Written-spec inspection is not rendered verification, user testing or conformance certification. Human-facing SVG comps remain deferred and would supplement the specification.

Keep this reference around 1,000 words. Add only guidance that changes decisions, with source/version or access date, evidence type, context and limitations. Numeric experiments require actual users/tasks/methods; a design-system convention is not an empirical result.

For the human-facing layout reference, use the [consolidated layout defaults](../../skills/refine-design/references/layout-defaults.md). Keep representative spacing and typography together, including component internals; the component reference owns appearance and state/color variations. The extractable baseline is a current editable design choice and yields to later app/component values without requiring an open question or acceptance step.
