## Questions and decisions

1. **How to verify the changed thread setting without exhaustion?** Compare user
   configuration with current runtime reporting: sixteen spawned threads plus
   primary. This verifies reported capacity, not every boundary error; no dummy
   threads were created to exhaust the host.
2. **How to retire without a closure tool?** Keep known or potentially open
   threads counted. Reuse compatible authors and reserve later roles. Explicit
   closure is tested only in the fake host, not claimed live.
3. **Where should evidence live?** Raw unrelated synthetic trial inputs/outputs
   stay under `.codex-tmp/agent-preparation/`. Commit only reusable code, tests,
   instructions and general findings. No real application data was added here.
4. **How much new rendering machinery is justified?** Reuse existing native
   renderer and Edge capture helper. Separate setup/capture faults from startup
   measurements; do not develop a new renderer to improve a timing result.
5. **Where is a useful preparation window?** UI role/schema/foundation loading
   can overlap actual UX work and review. Do not add parser work or delays to
   manufacture overlap.
6. **How to repair missing baseline model context?** The first packet omitted
   the structured model and the author reported placeholder hashes. Persist the
   actual source-derived model and real binding before acceptance. Keep setup and
   focused feedback-reference correction separate from comparative timing.
7. **Must lifecycle development idle during baseline correction?** Host creation,
   acknowledgment/follow-up and a real upstream window were already observed.
   Develop the independent happy path concurrently, but gate integration and
   milestone completion on valid native baseline evidence.
8. **Where to persist preparation before a validated plan exists?** Use a small
   ledger beside the application's coordinator. Early advice cannot fabricate
   plan validity or ownership; actual assignment still requires an exact claim.
9. **How to preserve UX when the source catalog changes?** Keep the existing
   invalidation rule. Initialize known source/model/foundation inputs upfront.
   Revalidate retained unchanged native bytes with actual author provenance and
   stopped confirmation rather than weakening that rule.
10. **What if literal transitions need value-specific variants?** The actual UX
    reviewer found missing choice transitions. The author made the minimal six
    value-specific frames for three outcome classes. Derive UI owners from the
    accepted UX; do not introduce deferred state/treatment assembly.
11. **Does a later-role candidate consume its own reserved slot?** Yes; otherwise
    reservation double-counts it. The three-UX-to-one-UI deterministic test proves
    the no-closure stage transition.
12. **How to bind writes without inventing a capability?** Hold the preparation
    assignment guard and retained-file exact native guard together. Service grants
    with unconfirmed revocation stay unresolved; file authority has its actual
    persisted channel and exact claim.
13. **Can failed or retired labels release capacity?** No. Positive absence or
    closure is required. Preserve actual role and contributor provenance after
    assignment resolution.
14. **How to recover a writer lock?** Require the exact lock token and positive
    evidence the owning process is dead. Elapsed time and unknown liveness do not
    justify deleting a lock.
15. **What affordable comparison is appropriate?** Predeclare forty-five minutes
