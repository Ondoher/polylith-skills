# Data Persistence

## Purpose And Applicability

<!-- rule: DATA-PERSISTENCE-001 -->
This standard applies when a repository stores application data in a database, including relational, document, key-value, embedded, or managed database systems. A repository enables it by including `data-persistence.md` in the named standards sets assigned to folders that own persisted data or its cross-boundary contracts.

<!-- rule: DATA-PERSISTENCE-002 -->
The rules apply to durable domain records, stable embedded entities, persistence adapters, database representations, API boundaries carrying persisted values, notifications derived from persisted values, and their fixtures. They do not prescribe a database product or require persistence where an application has none.

## Persistent Identifiers

<!-- rule: DATA-PERSISTENCE-003 -->
Every durable domain record and stable embedded entity has a canonical lowercase UUID v4 identifier generated by the owning application boundary before persistence.

<!-- rule: DATA-PERSISTENCE-004 -->
- Use the same canonical UUID string for database keys, references, domain contracts, transport contracts, notifications, and fixtures.
<!-- rule: DATA-PERSISTENCE-005 -->
- Do not rely on database-generated identifiers such as MongoDB `ObjectId`, auto-incrementing domain identifiers, or another engine-specific key as the application's authoritative identity.
<!-- rule: DATA-PERSISTENCE-006 -->
- A caller may submit a reference to an existing entity but must not choose the authoritative identifier for a newly created server-owned entity.
<!-- rule: DATA-PERSISTENCE-007 -->
- Generate identifiers with a cryptographically secure platform source. Inject an identifier factory where deterministic tests require control.
<!-- rule: DATA-PERSISTENCE-008 -->
- Bearer secrets, random tokens, database implementation metadata, and bounded semantic keys are separate contracts and are not UUID substitutes.

## Concrete Instants

<!-- rule: DATA-PERSISTENCE-009 -->
Every concrete instant crossing a domain, persistence, API, notification, or fixture boundary is a finite integer Unix epoch value in milliseconds. A named field holding an instant uses an `At` suffix.

<!-- rule: DATA-PERSISTENCE-010 -->
- Do not persist or transport JavaScript `Date` values, database-native date objects, ISO timestamp strings, or locale-formatted timestamps as application instants.
<!-- rule: DATA-PERSISTENCE-011 -->
- Durations, delays, and lead times are finite integer millisecond counts rather than instants and use names that express their meaning.
<!-- rule: DATA-PERSISTENCE-012 -->
- A recurring local wall-clock rule is not an instant. Preserve its bounded local-time, recurrence, and IANA-timezone inputs until it resolves to a concrete occurrence epoch.
<!-- rule: DATA-PERSISTENCE-013 -->
- Parse and format dates only at genuine ingress or presentation boundaries; do not introduce a second durable time representation for convenience.

## Persistence Boundaries

<!-- rule: DATA-PERSISTENCE-014 -->
The application owner validates and normalizes identifiers and instants before writing them and validates persisted values before treating them as current domain data. Database-specific driver values remain behind the persistence boundary.

<!-- rule: DATA-PERSISTENCE-015 -->
Keep one canonical representation for each persisted fact. Indexes, references, caches, projections, queue records, and audit records derive from that representation rather than maintaining an independently authoritative copy.

## Verification

<!-- rule: DATA-PERSISTENCE-016 -->
Cover the persistence contract with tests appropriate to the selected database and boundary:

<!-- rule: DATA-PERSISTENCE-017 -->
- generated UUIDs use the canonical representation and survive write/read/reference round trips;
<!-- rule: DATA-PERSISTENCE-018 -->
- invalid, noncanonical, database-generated, and caller-selected new-entity identifiers are rejected;
<!-- rule: DATA-PERSISTENCE-019 -->
- concrete instants survive domain, database, serialization, and notification round trips without representation changes;
<!-- rule: DATA-PERSISTENCE-020 -->
- non-integer, non-finite, date-object, database-native-date, ISO-string, and locale-string instants are rejected at their boundary; and
<!-- rule: DATA-PERSISTENCE-021 -->
- controlled identifier and clock sources make collision, ordering, recurrence, timezone, and daylight-saving cases deterministic where applicable.
