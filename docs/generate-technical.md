# Generate a technical guide

[`generate-technical`](../skills/generate-technical/SKILL.md) turns a frozen, validated technical context into a linked Markdown guide for developers and coding agents. It publishes under `documents/<product>/technical/` by default. Preparation and assessment happen first through [refine-design's technical mode](refine-design.md); this skill makes no product or architecture decisions.

The input is the `context.json` saved under `product/<product>/contexts/technical/<hash>/`. Run the publisher from the skill directory with `node scripts/generate-technical.mjs --context <context.json> --output <repository>/documents/<product>/technical`. It produces an overview, architecture and ownership, critical flows, cross-boundary contracts when present, decisions and open questions, and an implementation handoff. Empty content pages are omitted. The guide distinguishes observed source facts from selected and conditional target design, explains responsibility and failure behavior in prose, and connects first demonstrations to contracts that still need evidence. Product outcomes and evidence summaries appear inline, so readers need neither support data nor source files to follow the guide. The architecture diagram shows bound boundary/flow relationships. Each critical flow groups required behavior, sequence, owner-by-owner stages, recovery paths, and open questions; the sequence diagram is an aid to reading order, not an API contract. Contract records describe semantic inputs, results, invariants, and failure effects at risky boundaries without inventing method names or wire formats. The preparation records must contain enough rationale and consequences for a useful technical explanation; publication does not invent missing design detail.

The intended architectural explanation includes a product-specific map of proposed features, shared capabilities, and important conceptual models when the system and Polylith assessments support one. It should identify state authority and connect those responsibilities to product outcomes and technical boundaries, while labeling placement that remains provisional. The skill does not prescribe a feature tree or require view-level detail. If the source description and assessment support only a partial map, publish its limits and links instead of inventing missing structure.

Deep issues belong in separately authored technical white papers, such as a player architecture paper for a product whose media engine needs dedicated design. An authored paper stays at its supplied repository location; `documents/<product>/<doc-name>/` is reserved for generated publications. A current `White paper:` reference in the product description is bound to the paper's exact bytes. The publisher links each verified paper from the index and gives it a dedicated section on `focused-papers.md`. That section explains the technical records mapped from the paper. Unresolved paper questions use the same product, technical, or evidence gap records as primary-description questions, so they also appear in the shared decisions and implementation handoff pages. The paper and its research status stay visible even before its claims have been reconciled; the focused page then says the mapping is pending. Keep assessments and support records in `product/<product>/`. A link does not accept proposals as architecture. The publisher does not generate papers, and receipt-owned pages must not be hand-edited.

The publisher formats the pages with the destination repository's installed Prettier and resolved configuration before recording their digests. The `publication-receipt.json` lists every generated file and its digest. A repeat publication checks that the previous output is wholly generated and unchanged before replacing it; human edits or extra files stop replacement. Keep hand-authored notes in a separate directory, and re-resolve a technical context against the repository before publishing when source freshness matters. Publication rejects linked path ancestors. After an interrupted replacement it restores one verified backup; ambiguous or modified transaction files remain untouched for inspection. The technical-context test exercises stale and invalid inputs, ownership protection, rollback, and restart recovery.
